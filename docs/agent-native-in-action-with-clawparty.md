## 第一章：Agent-Native 是什么

### 1.1 Dan Shipper 的原始定义

2026 年 1 月，Every 的 CEO Dan Shipper 与 Anthropic 的 Claude 联合发表了《Agent-native Architectures: How to Build Apps After the End of Code》，首次系统性地提出了 Agent-Native 架构的概念。

**一个比喻**。Dan 将传统软件比作摩天大楼——每一根梁都经过荷载测试，每一股力和流都遵循蓝图。而 Agent-Native 软件更像**培育花园**——你播种、浇水、修剪，但花园最终长成什么样子，无法被完全预见和规定。核心差别在于：传统软件中，开发者写死每一步逻辑；Agent-Native 中，开发者描述**要达成什么结果**，Agent 自己决定**如何达成**。

**一个发现**。Dan 指出一个反直觉的发现：**一个优秀的编程 Agent，本质上就是一个优秀的通用 Agent。** Claude Code 证明了，只要给大语言模型访问 Bash 和文件系统的权限，让它在一个循环中运行直到达成目标，它就能自主完成复杂的多步骤任务。同样的架构——给 Agent 工具、让它循环执行——也可以用来整理文件、管理阅读列表、自动化工作流。

**五个原则**。Dan 和 Claude 将这套架构提炼为五个核心原则：

| 原则 | 要义 | 判断标准 |
|------|------|---------|
| **平权（Parity）** | UI 能做的事，Agent 必须能通过工具完成 | 随机挑选一个 UI 动作，Agent 能完成吗？ |
| **颗粒度（Granularity）** | 工具是原子级原语，功能是 Agent 在循环中组合工具达成的结果 | 改行为是改 Prompt 还是改代码？ |
| **可组合性（Composability）** | 有了原子工具和平权，仅靠写 Prompt 就能创造新功能 | 新功能能不能不写代码就实现？ |
| **涌现能力（Emergent Capability）** | Agent 可以完成你从未显式设计过的任务 | 描述一个你没开发过的功能，Agent 能搞定吗？ |
| **随时间进化（Improvement Over Time）** | 积累上下文 + 优化 Prompt，不发版也能变强 | 一个月后比第一天用得好吗？ |

**参考实现**。Dan 在文章中反复将 Claude Code 作为 Agent-Native 架构的参考实现。Claude Code 的工作方式是：

```
用户描述目标
    ↓
Agent 进入循环：
  读文件 → 分析 → 编辑代码 → 运行测试 → 检查结果
    ↓           ↑
    └── 不符合预期就继续 ──┘
    ↓
达成目标，退出
```

它的关键设计选择：Bash + 文件系统作为通用接口（Agent 天生理解 `cat`、`grep`、`mv`）；所有操作可检查（用户能直接看到 Agent 改了哪些文件）；自文档化（`/projects/acme/notes/` 这样的路径自携带语义）。

Dan 的原话总结了这一切：

> "That's why I often think of agent-native apps as **Claude Code in a trenchcoat**."
> ——把 Agent-Native 应用称为"披着风衣的 Claude Code"。

### 1.2 精确化定义

Dan 的原始定义侧重于"Agent-Native 软件架构"——即如何构建以 Agent 为核心的软件系统。

但在实践中，我们将这个概念进一步明确为一个更精确、更可操作的定义：

> **Agent-Native = 使用 AI Agent 完成某项确定的目标。**

拆解开：

| 要素 | 含义 |
|------|------|
| **使用 AI Agent** | 不是传统代码的 if/else 逻辑，而是具备判断力的智能体在循环中运行 |
| **完成** | 不是"尝试一下"，而是持续执行直到目标达成，包括处理中间出现的意外 |
| **某项确定的** | 目标具体、可验证、有明确的完成信号，不是模糊的"帮我想想" |
| **目标** | 结果是最终状态，不是执行步骤。你描述终点，Agent 决定路径 |

这个定义的关键在于：Agent-Native 的本质不是"如何设计软件"，而是**以 Agent 达成目标为核心的工作范式**。Dan 的五个原则是让这个范式**工作得好的工程条件**，但范式本身是更根本的东西——**把目标交给 Agent，而不是把步骤交给代码。**

### 1.3 从编程 Agent 到广义 Agent-Native

在实践中，我们发现了一个关键事实：

**编程 Agent 是重要的基础，但仅有编程 Agent 并不能完全实现 Agent-Native。**

Claude Code 在编程这个细分领域，验证并跑通了完整的 **Agent-Native Software Development** 闭环。这个闭环体现了所有五个原则——平权（Agent 能做开发者能做的一切）、颗粒度（原子化的文件操作和 Shell 命令）、可组合性（通过 Prompt 创造新工作流）、涌现能力（处理未预见的代码结构）、随时间进化（积累项目上下文）。

但当我们把这个闭环从"编程"扩展到更广义的"完成目标"，在每一个关键维度上，问题的复杂度都发生了质变：

| 维度 | 编程 Agent | 广义 Agent-Native |
|------|-----------|-------------------|
| **协作模式** | Coding Agent ↔ 代码仓库，单主体、单目标 | 广义 Agent ↔ 人类，多主体、多形态、网状协作 |
| **工具范围** | diff, sed, git, LSP……围绕代码的固定工具集 | 每个细分领域有自己特定的工具集，ClawParty 封装为 Agent 可调用的原语 |
| **工作对象** | 源文件（`.ts`、`.rs`、`.py`……） | 任意"事物"——设备、订单、房间、合同、数据流…… |
| **决策权** | Agent 有不同程度的自主权，但错了可以回滚——`git revert` 一键撤销 | Agent 的自主权形态相同，但决策的代价和约束复杂得多——合规、审计、不可逆的物理后果；ClawParty 提供混合评审框架 |
| **通信** | 终端 I/O，形态、信号、信息定义确定 | 多领域各有方言和信号机制，衰减、噪声、意图完整性是核心挑战；ClawParty 泛化编程 Agent 通信模式，以 ZTM 加密承载 |
| **知识** | 编程语言、工程范式与工具链——领域知识体系成熟且可自举 | 每个垂直领域都需要构建属于自己的"知识体系"；ClawParty 的核心能力之一是让 Agent 获取、整理和积累这些领域知识 |

下面逐项展开。

---

#### 协作模式

在编程 Agent 的世界里，只有一个 Coding Agent 和一个代码仓库。协作模式是单向的：人发指令，Agent 执行。

但在广义 Agent-Native 中，"Agent"不再局限于代码编辑器里的聊天窗口。**广义智能体**正在从三个方向涌现：

- **Coding Agent**——已经实现并验证的形态。Claude Code 证明了软件 Agent 可以在数字世界中自主完成复杂任务。
- **物理智能体**——正在高速发展。无人驾驶汽车、配送机器人、无人机、智能家居设备……它们正在从遥控工具进化为具备自主判断力的协作方。
- **互联网服务（SaaS 等）**——正在快速向智能体过渡。今天的 SaaS 是你操作的工具，明天的 SaaS 是你可以委派目标的对象。

这三类广义智能体与人类一起，构成了一种全新的协作网络：软件 Agent 负责分析和规划，物理智能体负责在现实世界执行，SaaS 服务负责提供数据和处理能力，而人在其中既是协作方（决策、审批、提供判断）、也是"工具"（当需要一双手把包裹交给快递员时）。

在这个网络中，ClawParty 扮演一个关键角色：**让存量的软件和设备变成智能体。** 通过可插拔的引擎架构和多协议通信层，ClawParty 可以将现有的 SaaS 服务、IoT 设备、甚至一段 Shell 脚本，快速接入到这个广义智能体协作网络中——不需要重写，只需要接入。

---

#### 工具范围

编程 Agent 的工具世界是有限的、已知的。无论是 Claude Code 还是 OpenCode，它们依赖的核心工具集大同小异——diff 比较差异、sed 文本替换、git 版本控制、LSP 代码分析、编译器和测试运行器。这个工具集的边界清晰，因为它们只服务于一个目标：修改代码。

但广义 Agent-Native 面对的是无穷尽的领域。每个领域都有自己特有的工具：

- **IoT 领域**：温度传感器、空调遥控器、智能门锁、灯光控制器
- **物流领域**：库存系统、路线规划引擎、快递面单打印机
- **金融领域**：交易接口、风控规则引擎、合规审核系统
- **医疗领域**：影像分析模型、电子病历系统、排班调度器

这些领域的工具形态各异——有的是 API，有的是硬件驱动，有的是遗留系统的命令行接口，有的甚至是"一个人"。关键不在于工具是什么形态，而在于 **Agent 能否像调用 `diff` 一样自然地调用它们。**

ClawParty 的做法是：**将任意领域工具封装为统一的可调用原语。** 无论底层是一个 SaaS API、一个 GPIO 引脚、还是一只快递机器人的控制指令，经过封装后，Agent 看到的都是一个标准化的工具定义——有名称、有描述、有参数 schema、有执行函数。对于 Agent 而言，调用"空调遥控器设定 24 度"和调用"sed 替换某行代码"没有本质区别。对于工具提供者而言，把现有软件或设备接入 ClawParty，就是让它"变成"了一个 Agent 可调用的工具。

这种封装也不排除人。在某些场景中，人就是最灵活的工具——"帮我把包裹交给快递员""请确认这份合同的关键条款""给客户打一个电话确认时间"。ClawParty 将人视为一种特殊类型的工具：通过消息通道下发任务，人在自己的界面中完成操作并标记完成，Agent 像等待其他工具返回一样等待人的结果。

---

#### 工作对象

编程 Agent 的工作对象明确且统一：源文件。读一个文件，改一个文件，跑一个测试。从开始到结束，Agent 操作的都是同一类东西——文件系统中的文本。

但广义 Agent-Native 的工作对象可以是任何"事物"：一台需要调温的空调、一批待配送的包裹、一间需要锁门的会议室、一份等待审批的合同、一段实时监控视频流。它们不是文件，或许不在文件系统里，甚至不在数字世界中。

这意味着 Agent 在开始工作前，必须先完成一步编程 Agent 几乎不需要做的事情：**识别并定位工作对象。** "把 3 楼的空调调到 24 度"——Agent 需要先知道"3 楼的空调"是哪个设备、它的标识符是什么、通过什么接口访问。这个过程是：**明确工作对象 → 从工具集中找到匹配的工具 → 执行操作。**

在 ClawParty 中，每个工具定义不仅描述"这个工具能做什么"，也描述"这个工具面向什么工作对象"。Agent 通过匹配工作对象与工具描述，自主选择正确的工具——就像编程 Agent 通过 `grep` 找到文件、再通过 `sed` 修改它一样自然，只不过工作对象从一个文件变成了一台空调。

---

#### 决策权

决策权的形态在编程 Agent 和广义 Agent-Native 中并没有本质不同——Agent 都可以在不同程度上拥有自主决策权，从"只读建议"到"自主执行"。差异在于决策的**代价和约束**。

编程 Agent 决定 merge 一段代码：如果错了，`git revert` 一键回滚。最坏的情况可能是一次生产事故，但它的后果是数字的、可逆的、可控的。

广义 Agent-Native 的决策不会这么简单。Agent 决定"关闭 3 号反应堆的冷却阀"——这没有 `revert`。Agent 决定"批准这笔 500 万美元的转账"——这需要审计签名。Agent 决定"让自动驾驶车辆变道"——这个决策背后是真实的物理风险和法律后果。

这些决策面临三层额外约束：

- **合规**：决策是否符合行业监管要求？是否在允许的自主级别之内？
- **审计**：谁做的决策？基于什么信息？是否有人审阅过？每一步都需要可追溯的记录。
- **责任归属**：当一个不可逆的决策产生了后果，谁来负责？

ClawParty 为这种复杂决策提供了框架和工具。核心是**混合评审（Human-in-the-Loop Review）**：Agent 被允许做什么，取决于操作的敏感级别。低风险操作（查询温度、读取日志）可以完全自主；中等风险操作（修改配置、发送通知）Agent 执行后将摘要推送给人类确认；高风险操作（物理设备控制、资金转账、合约签署）必须经过人类专家明确审批。审批不局限于 Web UI——人类专家可以通过 Telegram、Slack 或任何已接入的通道收到审批请求并做出决定。Agent 等待人类的判断，就像等待另一个工具的返回结果。

#### 通信

编程 Agent 的通信出奇地高效。人和 Agent 之间只有一个终端窗口——你打字，它回复，它汇报进展，你给出反馈。Agent 之间也简单：一个写设计文档，另一个读取后执行。通信路径短，信息密度高，噪声极低。

这不是因为编程场景天然简单，而是因为编程 Agent 的世界里，**通信的形态、信号和信息的定义都是确定的。** "信号"是什么——工具调用的返回码是 0 还是 1、测试通过了还是失败了、diff 显示改了什么——没有歧义。"信息"的格式是什么——标准输出、文件内容、JSON 结构——大家都遵循同一套约定。通信的参与者之间不存在"你听懂了吗"的问题，因为他们共用一套语法。

但在广义 Agent-Native 中，这套确定性消失了。每个细分领域都有自己独特的通信生态：

**领域方言与行话**。一个物流领域的 Agent 需要理解"干线""支线""中转""签收"这些术语的确切含义，以及它们之间的逻辑关系——"签收"意味着包裹已从"派送中"变为"已完成"，这会触发下游的结算流程。一个医疗 Agent 需要区分"医嘱""处方""病程记录"——它们看起来都是文本，但法律效力、操作权限、时效要求完全不同。编程 Agent 不需要处理这个：`function`、`class`、`import` 在任何代码仓库里含义相同。

**独特的信息传递机制**。有些领域的信息不是以文本传递的。工业控制领域用 MODBUS 协议定时轮询设备状态——信息是一个寄存器值的周期性变化，不是一条消息。金融交易领域的信息密度极高——毫秒级的价格变动本身就是一种通信，每一跳都携带决策信号。在这些场景中，Agent 需要做的不是"阅读消息"，而是**从领域的信号机制中提取信息**——就像编程 Agent 不仅读 stdout，也读退出码。

**非结构化的人类沟通**。人类之间的信息传递更复杂。"那个问题你帮我看一下"——"那个"指什么？"看一下"是要分析、要修复、还是只需要确认？人类依赖共享的上下文来消歧，而 Agent 需要意识到上下文可能不完整，主动追问、确认、复述，而不是假装理解。

ClawParty 将编程 Agent 中被验证有效的通信模式泛化为通用模型。核心是三个原则：

**最短路径引用**。Agent 不转发信息，它引用信息源。另一个 Agent 可以通过工具直接访问源头数据，走最短的路径而不是最长的传话链。这从根本上解决了信息衰减问题。

**分级信号通道**。高频的状态信息走事件流（Agent 之间自动消费），需要人类注意的决策请求走独立的审批通道。不是所有消息都值得人类的注意——Agent 学会区分"信息"和"信号"，抑制噪声。

**上下文注入**。在每次交互时，Agent 的系统 Prompt 中包含了当前可用的资源清单、领域术语表、最近的活动日志。Agent 不是在一个空白语境中回应，而是在一个充分配置过的上下文中理解"那个"指什么、"处理"的边界在哪里。

这些原则以 **ZTM 加密网络**作为物理载体。无论 Agent 之间是通过互联网还是局域网、通过 Telegram 还是 MQTT 通信，底层的通信逻辑一致：引用而不转发、分级而不广播、完整上下文而非空白推断。而领域方言、信号机制、非结构化沟通的适配，则通过 ClawParty 的工具封装层和领域知识管理（详见"知识"维度）来完成——Agent 不是天生懂行话，而是通过工具描述和 Wiki 系统获得了领域的"词典"。

#### 知识

编程 Agent 的知识世界是清晰的。编程语言有语言规范（ECMAScript、Rust Reference），工程实践有公认范式（MVC、微服务、领域驱动设计），工具链有标准体系（编译器、包管理器、LSP、CI/CD）。这套知识系统经过数十年的积累和标准化，已经高度结构化、可查询、可传递。一个编程 Agent 进入任何代码仓库，它不需要重新学习"什么是函数"或"怎样做版本管理"——这些是普适的。它只需要阅读这个项目的特定上下文：目录结构、依赖关系、业务逻辑。这就是编程领域"可自举"的含义——领域知识本身已成为基础设施，Agent 开箱即用。

但在广义 Agent-Native 中，绝大多数垂直领域还没有完成这种"知识基础设施化"。每个领域都面临同一个根本问题：**你需要让 Agent 理解这个领域，就像它理解编程一样。** 这远不止背几个术语表——它意味着 Agent 需要掌握领域的"语法"（事物之间的关系规则）、"标准库"（可用的工具和操作）、"设计模式"（处理典型场景的最佳实践）。而关键挑战在于，这些知识目前还不存在，或者说存在但尚未被结构化：

**知识的碎片化**。领域知识分散在多个彼此不互通的地方：操作手册在 PDF 里，业务规则在数据库的存储过程中，物理拓扑在工程师的脑子里，历史教训在 Slack 聊天记录里，合规要求在监管网站上。编程 Agent 只需要 `git clone` 就能拿到完整的知识上下文；广义 Agent 面对的是一个需要自己拼起来的拼图，缺了哪一块都可能导致错误判断。

**知识的隐性化**。大量领域知识是不可言传的。"这个泵在冬天容易冻住，得提前预热"——这条知识不在任何文档里，它只在老员工的经验中。"这个客户的订单永远是急单，不用问优先级"——这是销售团队心照不宣的默契。Agent 无法读取人的经验，除非这些经验被显式地记录和结构化成它可以消费的形式。这意味着 Agent-Native 的落地不仅要解决 Agent 的问题，还要解决"把隐形知识变成显式知识"这个组织层面的问题。

**知识的动态演化**。编程领域的知识变动有明确的节奏——语言版本升级、框架发布新大版本，变更可预期、有文档、有迁移指南。但垂直领域知识的演化是持续的、碎片化的、缺乏公告的。供应链规则因为一次港口罢工而临时调整，物业管理系统因为新租户搬入而变更了门禁规则，医疗流程因为一份新发布的诊疗指南而更新了用药方案。Agent 不能假定自己学到的知识是永恒的——它需要持续感知知识的变化，并主动更新自己的理解。

ClawParty 的做法是：**为每个领域构建属于它自己的"编程知识体系"。** 这不是一次性工程，而是一个伴随 Agent 运行的持续过程，通过双层知识架构实现：

**Wiki：结构化文档体系**。面向人和 Agent 共享的知识库。原始来源（PDF、网页、聊天记录、录音转录）首先存入 `raw/` 目录作为不可变的事实来源。Agent 在人类协作下将这些原始材料转化为结构化的 Wiki 页面——实体页描述领域中的"是什么"（设备、角色、位置、合同），概念页描述"为什么"和"怎么做"（业务流程、决策规则、操作规范）。页面之间通过 `[[WikiLink]]` 建立关联，构成一个可浏览、可查询的知识网络。这个网络本身也是可生长的——Agent 在解决问题时发现的知识空白，会被记录为待填充的页面；发现的知识过时，会被标记和修正。每个 Agent 通过系统 Prompt 中的 Wiki 方法论（WIKI.md）获得"如何阅读和维护这套知识体系"的指令。

**知识图谱：语义关系引擎**。Wiki 解决"文档化"问题，知识图谱解决"可计算"问题。图谱将领域的核心概念抽象为节点——模式（反复出现的问题结构和解法）、决策（在特定条件下做出的选择及依据）、教训（失败经历和从中提取的原则）、专家（掌握某类知识的人及其专长标签）——并以有向边连接它们（"使用""替代""扩展""适用于""由某人贡献"）。Agent 通过 `knowledge` 工具与图谱交互：执行任务前搜索相关模式以避免重复踩坑，做出决策时查询历史决策及其上下文以保持一致性，遇到不熟悉的子领域时定位专家并请求输入。图谱的每一次更新——每一条新捕获的模式、每一个记录下来的决策——都在降低下一个 Agent 面对同一领域时的认知门槛。

**渐进积累原则**。ClawParty 的知识体系不是"先建好再使用"，而是"边使用边建设"。第一个进入某个新领域的 Agent 几乎不具备领域知识——它只能依赖工具描述中携带的少量上下文，以及它从通用知识中推理出的合理假设。但随着 Agent 持续解决问题——查询设备状态、执行操作、记录结果、反思优化——每一条交互都在向知识体系注入信息。Wiki 中新增的页面、图谱中新增的节点和边、AGENTS.md 中沉淀的方法论，都在使下一个 Agent 对这个领域的理解更完整。这是 Agent-Native 原则中"随时间进化"在知识维度的具体体现：不是代码在变好，而是知识在积累，Agent 在利用更丰富的上下文进行更精准的判断。

### 1.4 专有 Agent：为每个领域构建属于它自己的 Agent

回顾以上六个维度的展开，一条清晰的路径浮现出来：ClawParty 为每个细分领域、每个行业构建属于自己的**专有 Agent**，提供了一套完整的方法论以及配套的工具链。这条路径涵盖了五个核心方面：

**知识**——该领域的知识体系，包括知识的获取和持续更新。ClawParty 通过双层知识架构（Wiki + 知识图谱）让 Agent 能够像理解编程一样理解一个行业，并且知识不是一次性灌入，而是在 Agent 的每一次交互中持续生长和演化。

**通信**——该领域的通信体系，既包括物理层面的通信能力（Agent 之间如何连接、通过什么通道传递信息），也包括语义和逻辑层面的通信机制（该领域的术语体系、信号编码方式、信息传递惯例）。ClawParty 将编程 Agent 中验证有效的通信模式——最短路径引用、分级信号通道、上下文注入——泛化为通用模型，并以 ZTM 加密网络承载。

**工作对象**——识别和定义该领域的核心"工作对象"，就像源代码对于编程领域一样。每一个行业都有自己需要操作的原生"事物"——设备、订单、合同、病人、房间、包裹——Agent 必须知道它操作的是什么、如何定位它、如何引用它。ClawParty 的工具描述体系将工作对象与工具绑定，使 Agent 能够像定位文件一样自然地定位领域对象。

**工具**——该领域专有的工具集。这可能涉及定制和开发新的工具，但在有了编程 Agent 之后，这些工具的识别与制作难度已经大幅下降——描述一个工具的接口和行为，让 Agent 去实现它，这本身就是一个 Agent-Native 的工作流程。ClawParty 的统一工具封装层使得任意领域的工具——无论是 SaaS API、硬件驱动还是人的操作——都可以被标准化为 Agent 可调用的原语。

**协作与决策**——该领域常用的协作模式与决策方式。Agent 不是孤立工作的，它嵌入在一个由人、其他 Agent、SaaS 服务、物理设备构成的协作网络中。谁能做什么、谁审批什么、什么情况下需要人介入——这些规则本身就是该领域"专有 Agent"不可或缺的一部分。ClawParty 通过混合评审框架、分级审批通道和可配置的决策边界，让协作与决策模式可定义、可演化。

这五个方面不是各自独立的，而是相互缠绕的——工作对象的定义影响工具的封装方式，通信体系承载协作与决策的信息流，知识体系为所有维度提供上下文。ClawParty 的方法论要做的，就是让这五条线索在每一个垂直领域中构成一个自洽的整体，使 Agent 从"能编程"走向"能胜任这个领域的工作"。

### 1.5 如何使用本文档

**本文不仅为人类读者而写，也为 AI Agent 而写。**

这不是修辞。本文的每一章都在阐述一套可操作的方法论——Agent 生命周期管理、混合工作模式、零信任安全、通用能力体系。人类读者可以从中理解 Agent-Native 的落地逻辑；而当你将本文连同你的目标一起提交给 ClawParty 时，Agent 会基于这套方法论开始工作：

```
你的目标 + 本文（方法论）→ 提交给 ClawParty
    ↓
Agent 读取本文，理解范式、原则和工具
    ↓
Agent 根据目标制定执行策略
    ↓
Agent 使用 ClawParty 提供的工具链进入循环，直到目标达成
```

这意味着本文既是**说明书**，也是**配置文件**。它定义了 ClawParty 中 Agent 的工作方式、安全边界、协作模式和知识体系。如果你想定制 Agent 的行为，修改这篇文档比修改代码更直接——这正是 Agent-Native 原则中"可组合性"和"随时间进化"的体现。
